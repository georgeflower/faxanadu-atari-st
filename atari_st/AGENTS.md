# AGENTS.md - the briefing for anyone working on the port

Read this before researching anything. When you learn something durable, add it here. `CLAUDE.md` in the repository root only points here.

## 1. What this is

A native **Atari ST (520 STFM, 512 KB, 68000, PAL 50 Hz)** port of **Faxanadu (NES)**, in 68000 assembly (GNU as syntax) with a Python asset pipeline that reads graphics, maps, palettes, text and music from **a ROM you supply** (`ext/Faxanadu_Europe.nes`, gitignored, never committed). The result is a stock TOS `.PRG`: 320x200, 16 colours, YM2149 sound.

It follows the Zelda 1 port (`georgeflower/zelda1-atarist`): same method, same tools, same rules.

The rest of the repository is chipx86's labelled disassembly of the **US** version (`src/*.asm`, builds with `make` in the root). It is the **spec for every behaviour**: when you need a number (speed, timer, damage, tile id, table), read it there, never guess.

Status: set-up, the ROM harness, the map data decoder and a viewer that draws one screen with its HUD and the hero on the ST. `src/main.s` is a start-up check that shows 16 colour bars. What comes next is in `PLAN.md`.

## 2. Rules

1. **The ROM is the reference for behaviour.** Read values from the disassembly, then check them in the ROM. The port "improving" on the ROM is a bug report later; match first, change only when asked, and write deliberate differences down here.
2. **All game data comes from the user's ROM.** Nothing from the ROM (images, tables, music) is committed. Tests keep sizes and hashes. If the ROM is missing the build stops; no stand-in art.
3. **Build and test headlessly, always.** Assemble, run in Hatari, compare frames with golden hashes, run the unit tests. A disk image the user has not seen built and run is not delivered.
4. **The 16-bit branch limit wraps silently** in GNU as and ld. `tools/check_reach.py` runs on every link; do not disable it.
5. **Budget first.** An STFM has no blitter and no hardware scroll; a frame is about 160,000 cycles at 50 Hz. Estimate the cycles of anything per-frame before writing it and measure afterwards.
6. **No version numbers** anywhere (no VERSION, no CHANGELOG, no version line in docs). The author tags releases himself.
7. **Commit straight to `main` and push; no pull requests** (the author's decision, Nov 2026; stacked pull requests had merged into their base branches and never reached `main`). Run `make check` first. Disk images are named `Fax###.st`, ### = the build number = the number of commits (`git rev-list --count HEAD`, three digits): `make disk` for the game, `make viewerdisk` for the viewer. Commits end with the `Co-Authored-By` line and no session link.
8. Docs are short and plain, in the author's voice, and never name him: write "the author". One line on the AI help, no details of what was tested by hand.

## 3. Which ROM

The ROM the port reads is **Faxanadu (Europe)**, PAL, because the author's ST is PAL and runs at 50 Hz like the PAL NES: one game tick per VBL, no pacing tricks. (At 60 Hz, hold one VBL in six.)

The disassembly is the US ROM. They match closely (`tools/rom_diff.py US-ROM EU-ROM`, counts only; the US ROM is what `make` in the root builds, `ext/` is not needed for it):

| bank | what | Europe versus US |
| --- | --- | --- |
| 0-4, 6-11, 14 | area data, area metadata, sprites, CHR RAM tiles, sprite info and palettes, game logic | identical |
| 5 | audio logic and music data | 13,371 bytes differ (not looked at yet) |
| 12 | game logic, interaction scripts, start screen, password | 5,774 bytes differ (texts and the start screen's code) |
| 13 | strings and font | 397 bytes differ (the font is redrawn) |
| 15 | fixed bank | 12 bytes differ: the bank-call code's zero-page variables move by four, three far-call pointers change (the start screen's code moved in bank 12), and a stray padding byte and two bytes at the end of the ROM |

So the disassembly is a valid spec for nearly all logic. For data, **search the Europe ROM for what is needed; do not trust US offsets** (the Zelda port learned this with Rev 1). Where bank 5, 12 or 13 are involved, check the Europe ROM itself.

The iNES header of the Europe ROM: NES 2.0, mapper 1 (MMC1), 16 PRG banks (256 KB), no CHR (CHR RAM), PAL timing, horizontal-mirroring flag set (the disassembly's header says vertical; MMC1 sets mirroring at run time, so which one the game uses is [to check]).

## 4. The disassembly

- Build: `make` in the root needs `cc65` (`ca65`, `ld65`); it writes `build/faxanadu.nes`. The file `src/HEADER.asm` is named in capitals because `faxanadu.asm` includes it that way (a lower-case name broke the build on Linux).
- Banks (`DEFS.asm`): 0-2 area data (maps), 3 area metadata, 5 audio logic, 6-8 sprites, 9 unused, 10 CHR RAM (tile data), 11 sprite info and palettes, 12 logic, 13 strings, 14 logic, 15 the fixed bank at `$C000`, the biggest (about 30,000 lines).
- Areas (chipx86's notes, "Levels"): Eolis, Forepaw, Mascon in bank 0; Apolune, Conflate in bank 1; Daybreak, Victim, Evil Fortress in bank 2. The current screen's block data is at `$0600-$06FF`. Blocks have 16 kinds (air, solid, ladder, door, transition up/down/left/right ...). Block data is compressed [format to read in the disassembly].
- Notes by chipx86: <https://notes.chipx86.com/Projects/Reverse-Engineering+Projects/Faxanadu+Disassembly/-Overview-> (Levels, Sprites, Palettes, Music Scripts, Interaction Scripts, Passwords, Strings, Memory). Tools: <https://github.com/chipx86/faxanatools/>, level editor and format doc <https://github.com/kaimitai/faxedit/>, interaction script tools <https://github.com/kaimitai/FaxIScripts>. Not all of these could be fetched from the cloud session; ask the author to attach what is needed.

## 5. Facts read from the disassembly (US)

- **Scrolling is between screens** [verified in the ROM, `tools/refnes/scroll_probe.mjs`]. In normal play the camera is still. Leaving a screen costs 14 frames of preparation and then exactly 64 frames of 4 pixels (`Game_MainLoop` runs `Screen_HandleScroll` four times a frame, one pixel each), 256 pixels in all, with nothing else going on. The Europe ROM and the US build do the same. Vertical scrolls wrap at `$D0` = 208 lines (read in the code, not yet measured). `Screen_HandleScroll` has two more callers that are not read yet.
- **The picture is a 32-line HUD on top of a 256x208 playfield** (NES screen 256x240) [verified in a jsnes screenshot; the HUD is split from the playfield with a sprite-0 hit]. 208 lines do not fit 200, and the HUD would come on top: the main design question for the display (see `PLAN.md`, step 4).
- The hero starts on a first screen with no neighbouring screens (`Area_ScreenToTheLeft/Right/Above/Below` all `$FF`); the castle door at x 192 (Up) leads to Eolis, screen 1, which has screens on both sides. Eolis is area 0.
- Interaction scripts: a script language runs all NPC and item interactions (`IScripts_*`, `IScriptAction_*`). The port should run the ROM's own scripts through a small interpreter, not hand-code each dialogue.
- Passwords: `IScriptAction_ShowPassword`; the format is in chipx86's notes.

## 5b. The map data, decoded [verified: pixel-exact against jsnes on two Eolis screens]

`tools/faxanadu_rom.py` finds tables by the disassembly's label names (names, addresses and file offsets only are cached, never ROM data) and reads the bytes from your ROM; `tools/faxanadu_maps.py` decodes areas and screens; `tools/render_screen.py` draws a screen from them with no emulator. `tools/refnes/refshot.mjs` makes the reference picture (and the sprites on it) from the harness.

- There are **8 areas** with 272 screens: 9, 64, 83, 14, 10, 40, 32 and 20. Their tilesets are 0 Eolis, 2 Trunk, 3 Mist, 5 Towns, 6 King's room/guru/hospital (buildings), 1 Branch, 4 Dartmoor and 4 again for the last area (the names of the areas themselves are not read yet).
- A screen is **16x13 blocks of 16x16 pixels**. Its block ids are compressed: two control bits per block, most significant first: 0 copy the block to the left, 1 the one above, 2 the one above and to the left, 3 read the next 8 bits. Offsets wrap in a 256-byte buffer; the last three rows are zeros (`Area_LoadBlocks`).
- An area's tables are in bank 3 (`AREAS_TABLE_PTR` then per area: five pointers to the block attributes and four block lists, block properties, scrolling data, door locations, door destinations). The block data is in banks 0-2 (`AREA_TO_SCREEN_DATA_BANKS`, `AREA_TO_BANK_OFFSET`). Pointers in a bank are the CPU address minus `$8000`.
- A block is four tiles (lists 1 to 4: top left, top right, bottom left, bottom right) and one attribute byte holding a palette number for each corner of a 2x2 group of blocks; the block's own corner is picked by the parity of its column and row.
- The tileset of an area is plain NES 2-bit tiles in bank 4 (`TILE_INDEX_TO_ADDR`, 4 to 8 pages of 256 bytes; all nine tilesets are 16 KB) loaded at `$1800`, which is tile `$80` of the background pattern table at `$1000`. Buildings load theirs at `$1A00`. Tile 0 is blank.
- Background palettes: `PALETTE_TILES_*` in bank 11, 16 bytes (four palettes of four NES colours); the area's default is `AREA_PALETTE_INDEXES`. Whether single screens use another one is [to check]. The harness' colour table is in `tools/nes_palette.py`.
- The jsnes picture differs from the data in three places that are not data: sprites (the hero and NPCs), the outer 8 pixels on each side, and the last 8 lines of the playfield (jsnes shows the NTSC window and blanks them; on a PAL TV they are visible). `render_screen.compare` leaves these out.
- **Screen neighbours** [verified against the game's RAM]: four bytes a screen in the area's scrolling data: left, right, above, below, `$FF` for none (`Area_LoadScrollData`). Seven of the links are one-way (area 1 screen 27, area 2 screen 38, area 7 screens 1, 12, 17); all others are mirrored.
- **Block properties** [verified against the game's RAM]: 256 bytes a area (one per block id, value 0-15; the game packs them two to a byte). Eolis uses 0, 1, 3 and 4. From chipx86's notes (not checked here): 0 air, 1 solid, 2 ladder, 3 door, 10-13 the screen transitions (up, down, left, right).
- **Doors**: records of four bytes ended by `$FF` in the area's door locations: screen, block position (row*16+column), destination index, start position (high nibble Y/16, low nibble X/16: where the hero stands on arrival). The destination (four bytes at index*4 in the door destinations; area 3 is 32 too high): new screen, palette, key requirement, and a byte not read yet. Verified for the castle door of Eolis (screen 0, block 156 -> screen 1, hero at 144,144); indices of 32 and up (doors into buildings) are decoded the same way but not checked. A new screen's **palette** comes from the door; scrolling between screens keeps it.
- **HUD and letter tiles**: 60 tiles at `HUD_TILES_START` in bank 10 are written to the background pattern table's first 60 tiles. They equal the game's CHR RAM except tiles 12 and 13, the bar tiles, which the game draws into CHR RAM as the bars fill.
- Still to find: the enemy and NPC sprite tiles (banks 6-8) and the per-screen sprite placements, what the other property values mean, doors into buildings, text (banks 12 and 13 differ in Europe).

## 5c. The HUD [verified against the game's own drawing and a jsnes picture]

- The HUD is rows 2 and 3 of the nametable (screen lines 16 to 31; rows 0 and 1 are blank), drawn with one of the four background palettes: `PALETTE_INDEX_TO_UI_BG_ATTRIBUTE_INDEX` (bank 11, `$81F0`, one byte for each of the 28 palette sets).
- Row 2: `M:` (tiles `$1C $0A`), the magic bar (columns 3-13), `E:` and the experience (5 digits, columns 16-20), `T:` and the time in seconds (2 digits, columns 24-25), the item box top `$2C $3C $3D $2E` (columns 27-30). Row 3: `P:` (`$1F $0A`), the power bar, `G:` and the gold (7 digits, columns 16-22), the item box bottom `$2D $3E $3F $2F`. Digit n is tile `$30 + n`; the item box's inner tiles `$3C-$3F` are the selected item's picture (blank with no item).
- A bar is 10 tiles and an end tile `$0B`: value>>3 full tiles (`$08` power, `$09` magic), then, unless the bar is full (value 80), one partial tile (`$0C` power, `$0D` magic) and empty tiles (`$07`). The partial tile's pattern is written into CHR RAM for value & 7 from `STATUS_BAR_PARTIAL_PPU_TILES` (16 bytes an entry; the magic bar's has the two halves swapped). HP and MP are capped at 80.
- `tools/faxanadu_gfx.py` makes the layout and the tiles; `tools/refnes/hudshot.mjs` sets values and runs the game's own routines in the harness (`g.call("UI_DrawGoldValue")`, which pushes the return address and jumps from where the main loop waits). Five states (HP, MP, experience, gold, seconds) came out tile for tile the same.

## 5d. Colours and the first picture on the ST [verified]

- **16 colours are enough.** A palette set (four background and four sprite palettes of four NES colours, `tools/st_convert.py`) has 9 to 19 different colours after rounding to the ST's 3 bits a channel. Merging the closest pairs down to 16 changes at most three colours, each by one step in one or two channels (squared distance 2 at most), in all 28 sets. So **one 16-colour palette per palette set**, slot 0 black, no raster tricks. Enemy sprite palettes that the screen loads on top (`Screen_LoadSpritePalette`) are not counted yet.
- **Block images**: a 16x16 block as 16 lines of four plane words (128 bytes), made for each (block id, corner) pair a screen uses, because the attribute byte gives a block a different palette in each corner (parity of column and row). Eolis screen 1 needs 59 images (7.5 KB); all nine Eolis screens 282 (36 KB).
- **The viewer** (`make viewer AREA=0 SCREEN=1 CAMERA=40`, `src/viewer.s`, data from `tools/build_assets.py` into `build/generated/`) draws the HUD (as at the start of a game) and under it the playfield window, 256 pixels wide in the middle of 320. It equals the converter's expected picture pixel for pixel in Hatari (`tests/test_viewer.py`, needs a TOS image in `TOS`). It is a plain loop (block by block, line by line), not tuned.
- **The HUD updates from a state block** (`src/hud.s`, `hud_update`): `hud_state` is 10 bytes (HP.b, MP.b, experience.w, gold.l, seconds.b, pad.b; `st_convert.hud_state_bytes`). The routine builds the 128 tile ids of the HUD layout (bars of 10 tiles + end tile, digits as tile $30+n, partial bar tiles from `hud_partial` copied into slots $0C/$0D), and draws only tiles that differ from `hud_shown` (the two partial tiles always). Test: `tests/test_viewer.py` cycles six states and compares with `expected_screen`. The viewer shows state A then B (`make viewer HUD=.. HUD2=..`).

- **The frame loop and the input** (`src/frame.s`, tests in `tests/test_frame.py`). `frame_init` (supervisor mode) replaces the VBL (`$70`) and the keyboard (`$118`) vectors; `frame_exit` gives them back and empties both ACIAs (otherwise the desktop has no keyboard). The VBL only counts (`frame_count`); `wait_vbl` waits for the next one and counts VBLs that passed before the call in `late_frames` (the harness reads it). The keyboard interrupt queues every byte in a 256-byte ring; `input_poll` (once a frame) parses it: joystick 1 packets (`$FF`, state byte: bits 0-3 up, down, left, right, bit 7 fire), joystick 0 (`$FE`, the mouse port) and mouse moves (`$F8-$FB` + 2 bytes) are skipped, everything else is a scan code (bit 7 = release). It makes `pad` in the NES layout (A $80, B $40, Select $20, Start $10, Up $08, Down $04, Left $02, Right $01) and `pad_new` (pressed since the last poll). **Buttons (a deliberate difference, one fire button on an Atari stick): fire = B (sword), stick = d-pad; keys: arrows = d-pad, Space = A (jump), Alternate = B, Return = Start, Tab = Select, Esc quits.** How a stick-only player jumps is open (G4). Tested: the parser on machine68k (mouse bytes that look like headers, a press and release within one frame, ring wrap, `wait_vbl` late count) and in Hatari that 100 VBLs give a `frame_count` delta of exactly 100 with no late frames.

- **Sprites over a still background: two screens and a clean copy** (`src/viewer.s`). The program asks TOS for three screens behind its image (`BUFFER_BYTES`, Mshrink; the first 256-byte aligned): two to show and draw alternately (`buf_a`, `buf_b`) and the playfield (`pf_ptr`, 208 lines, see below). Each frame: poll input, move, **erase** the rectangle the hero was drawn in two frames ago in the screen being drawn (`restore_rect` copies whole 16-pixel groups from the playfield at the camera line, clipped to the window), draw him (`draw_hero`: the pose's sprite list, positions relative to his x and y), `wait_vbl`, write the video base (`show_screen`), swap. The poses come from `st_convert.hero_anim_assets` (six: walk frames 0-2, right and left, made at x = y = 128 so nothing wraps at 8 bits; each with its bounding box). Demo movement only: 2 px a frame, no physics (`hero_step`); it is what the game's logic will replace. Tested in Hatari: the start pose equals the converter's picture for several equipments and pixel phases, and a stick pushed through the debugger (poke `IN_JOY`) walks him to the limit and leaves no trail. **The HUD in the loop**: the game writes `hud_state` and sets `hud_dirty`; the loop then calls `hud_update_all` (`hud_build` once, `hud_draw` into both screens, each with its own `hud_shown_*` list), right after the VBL so the beam has not reached the HUD yet. Tested by poking both through Hatari's debugger.
- **Cycles** (`tools/bench.py`, `make viewer VIEWER_DEFS="--defsym BENCH=100"`, German TOS for 50 Hz): drawing the hero (about 14 tiles) took 45,000 cycles with the two-group blitter and **25,600 with the one-group path** (shift 0-8 pixels, a tile fits one word a plane); shifts 9-15 still take the long path. A frame is 160,000. The erase is about 6,000. Next: compose a pose once into a wider mask-and-planes image and shift that.

- **Scrolling between screens** (`do_scroll` in `src/viewer.s`; ROM facts from `tools/refnes/scrollshot.mjs`, which records the scroll frame by frame in jsnes). The ROM waits 14 frames, then moves the picture 4 pixels a frame for 64 frames (offsets 4, 8 ... 256). The hero is not walking: he keeps his place in the world and the picture moves under him, his sprites 4 pixels ahead of the picture (the first sprite's x is 269 - offset in the first walk frame, 261 - offset in the second, going right; the left scroll is the mirror). The walk frame changes every frame. The picture lags the scroll register by one frame. **On the ST: 16 pixels every 4 frames** (the same speed, a quarter of the frame rate; this needs the author's eyes on the real machine). A step is four frames: (1) the playfield `pf_ptr` is shifted one 16-pixel group in place (the window's lines) and the next group of the new screen (drawn once, whole, into `next_ptr` at the start) is put in at the other end (about 110,000 cycles); (2, 3) the window is copied from the playfield into the screen being drawn, half each frame (about 70,000 each); (4) the hero is drawn (right: PosX = 261 - offset, left: offset - 20) and the screen shown. At the end both screens hold the new picture with the hero at his place on it (1 or 241). `present_swap` shows the screen, draws a changed HUD and swaps. Sprites are cut as the game does: a tile that starts outside x 32-287 on the ST (the playfield) is not drawn (the game skips cells that do not fit a byte); one reaching over the right edge is cut by `clear_margins`. `build_assets.py` includes the screens within `--reach` 2 steps of the start screen and a neighbour table (left, right, up, down as table numbers, `$FF` none). The viewer scrolls when he stands at x 8 or 241 and the stick is pushed that way. Tested in Hatari for both directions (the whole picture at 10 moments against the converter's picture: both screens side by side at the offset the program reports, the hero, no late frame). **Up and down** (`do_vscroll`). The ROM changes nothing for the hero except his y: `Player_PosY` is set at once to $C0 (going up: the bottom of the new screen) or 0 (going down), and the picture moves 208 lines at 4 a frame under him (`Screen_HandleScrollUp/Down`, nothing moves the hero during it; triggers: PosY wraps below 0, or passes $C0). The ST puts the two 208-line playfields one after the other in memory (above: the new one first; if the old one lies on the wrong side it is copied across first), `view_src` points at the window's first line in them and moves 16 lines every 4 frames (`copy_window_half` copies from `view_src`); the hero is drawn with the end camera. The window is 168 high, so the scroll covers about 168 lines in 11 steps, not 208. **Camera**: the window follows the hero in two positions, 0 while his y is under 56 and 40 above 120 (unchanged between; only once he has moved); a change sets `camera` and redraws both screens (`refresh_screens` twice, six frames). The test (`tests/test_viewer.py`, Trunk screen 3 and 4) compares the picture at ten moments of a scroll up and one down with `expected_vscroll_screen`, and the end state. The other callers of `Screen_HandleScroll` need nothing more: the main loop's horizontal scroll (four calls a frame) and `Screen_UpdateForScroll` (up and down) are what the tests compare with jsnes, and `Game_UpdatePlayerOnScroll` is the hero's sprite moving 4 pixels in the first four frames, which is the 269 - offset above; the call in the screen load only draws the screen, which the ST does at once. Not done: the 14 waiting frames show a still hero.
- **Walking** (C1/C2, `tools/hero_physics.py`, `src/viewer.s` `hero_step`; the golden run is `tools/refnes/walkgolden.mjs`, the test `tests/test_hero_physics.py` matches position, fraction, acceleration, flags and tick frame by frame). Positions are 8.8 fixed point. Walking starts with an acceleration of $C0 (0.75 pixel a frame), +2 a frame (+4, 6, 8 for the higher rank groups, `PlayerTitle` >> 2) until $180 (1.5 pixel); it starts again from $C0 after he stood still. Right is tested before left. His box is 16 wide and 32 tall (the block rows his y touches, three when y is not a multiple of 16): walking right a block 16 pixels in front of him stops him on his block's edge, walking left the pixel in front of x does the same (the next edge to the right). A wall is any block whose property is 1, 5, 6, 7, 8 or 11 (`BLOCK_PROPERTY_IMPASSABLE_MAP`); the package has the flags a block id (`block_flags`: 1 impassable, 2 a ladder) and `pkg_attach` expands them into a flag a block position behind the package (`screen_flags`: a screen's 208 impassable and 208 ladder flags, made when asked for and kept for 6 screens in `PACKAGE_EXPAND` bytes behind the package) so the disk does not carry them. Screen change: right when x is 241 or more after the move, left when the move runs off 0. Walking right at x 240 or more and walking left at x 0 test the neighbour screen's edge column (`FirstColumnInRightScreen`, `LastColumnLeftScreen`, block ids a row; `edge_blocked`, the `edges` table of the package): a wall there stops him at the edge, no neighbour counts as free; leaving to the left starts on the step that runs off 0 (`hero_off`) and a wall holds him at 0 (`hero_wall`). The acceleration steps by the rank group (`PlayerTitle` >> 2, `TITLE=n` for tests; there is no experience yet). There is **no crouching and no stairs in the game's movement code** (body frame 3 is the pose in the air), so there is nothing to port. The ST demo no longer clamps x (8 to 241 before).
- **Jumping and falling** (C3, `hero_physics.vertical_step`, `hero_vertical` in `src/viewer.s`; the golden run adds a standing and a running jump, a jump into a ceiling, a fall from the air and a hole in the floor, patched into the screen by hand). Feet: the block under the middle of the box (x + 4) at y + 32, and the next one when x & 15 is 4 to 11; beyond the screen's bottom the first row of the screen below counts, above the top the last row of the screen above. A new A press on the ground starts a jump when nothing is just over his head; the jump curve moves him up 8,4,4,4,4,2,2,1,1,1,1 then 0 five times, down 0 five times, 1,1,1,1,2,2,4,4,4,4,8 (32 frames, index 16 is the top); a head against a block turns him down (y set below the block when it was not on a block row); he lands on the block row when the feet find something. With nothing under him and no jump he falls 8 lines a frame. In the air he cannot turn: he goes on the way he went (the moving flag), standing still he goes straight. Over the top or bottom of the screen with a neighbour `scroll_check` scrolls (`vscroll_req`), without one he stops at the edge. The pose in the air is frame 3. A jump over the edge of the screen scrolls in the middle of the jump: the curve index and y stay frozen during the scroll and go on afterwards (golden run `tools/refnes/airscroll.mjs`, Hatari test). The ROM's wrong-register quirk in `Player_HandleVertLadderOrJump` (it loads A instead of X before the "block below" check) is not reproduced because it cannot be seen: X is only 0 to 2 when a ladder was found in the top left blocks, and then every outcome of the check ends in the same ladder grab (checked with jsnes: the ROM and a copy with the register fixed give identical runs over 6900 frames of ladder cases there). `make viewer VIEWER_DEFS='--defsym NO_PHYSICS=1'` keeps him where he is put (the picture tests use it; then up and down held move him 2 pixels, as in the first demo).
- **Ladders** (C4, `check_on_ladder`, `climb_up`, `climb_down`; model and golden run as above, with a ladder patched into Eolis screen 1: climbing, stepping to a ladder from the side, A does nothing on a ladder, climbing over the top of one). A ladder is a block with property 2 or 10 (`block_flags`). Can Climb is set when one is at his head or his feet (x + 7; the next block too when x & 15 is 8); Climbing (bit $10) is set when up or down is pressed with it and stays until the ladder is gone. Square on the ladder (x & 15 = 0) up lifts him 5/8 of a pixel a frame, down lowers him 3/4 (the ROM's comments have the wing boots the wrong way round); otherwise up or down walks him to it at the standard speed (left when x & 15 is below 8) while he hangs; with a ladder he does not fall off ledges. The movement tick counts walking and climbing frames (`hero_mtick`). **Wing boots** (Player_StatusFlag bit 7; `TITLE_TO_WINGBOOTS_DURATION` 40, 30, 20, 10 seconds by `PlayerTitle` >> 2, a second is 64 frames; golden run with the status bit set by hand, Hatari test): with the boots on the ladder goes a whole pixel up and 1 1/2 down a frame (the ROM's comments have it the wrong way round); with A also held up and down fly a pixel and 1 1/2 a frame whether there is a ladder or not, nothing under him he glides down a pixel a frame (8 without A), and he steers left and right in the air as on the ground; the pose is frame 3. On the ST the seconds are `hero_wings` (-1 none; `WINGS=n` at the start or the W key for the rank's time until there are items); the time on the HUD is not drawn yet. A door beside the ladder block hung the ROM in the harness (the PPU buffer filled): the golden ladder stands in column 13.
- **Poses** (`hero_pose`, `POSE_FRAMES` in `st_convert.py`): sixteen poses, the ROM's body frame (0 to 7) + 8 * flip: the walk frames 0, 1, 2, the frame in the air (3), the three attack frames (4, 5, 6) and the climbing frame (7, mirrored every 16 movement ticks). The rule is `Player_GetBodySpriteFrameOffset`: jumping 3; climbing (Can Climb and Climbing set, and not falling off while off the block grid) 7; walking the frames 0, 1, 2, 1 from `(tick >> 3) & 3`; standing 0. The climbing pose is compared with the converter's picture in Hatari, not yet with a ladder in jsnes. 
- **Attack** (C5, `hero_attack`, `attack_step` in the model; golden run: standing, walking and in the air). B pressed (not held; fire on the stick, Alternate on the keyboard) starts an attack unless he climbs: three phases of 8, 3 and 8 frames (body frames 4, 5, 6; the third adds the arm piece), the button must be let go before the next one. On the ground he stands still during it, in the air he goes on. Tested in Hatari: the three poses with the sword equal the converter's pictures. ## 5e. The hero's sprites [verified against jsnes: tiles, sprite list frame by frame, picture pixel for pixel]

`tools/faxanadu_sprites.py` follows the game's own routines and needs nothing but the ROM.

- **Tiles.** The hero has no fixed set of pictures. `Player_LoadArmorTilesToPPU` and its kin copy tiles from bank 8 to the sprite pattern table: a list of tile ids per armour (`TILES_PLAYER_ARMOR_ADDRS_INDEX`, entry = armour*2, plus 1 with a shield; the Battle Suit has one list; the count is `PLAYER_ARMOR_TILE_COUNTS` + 1) to pattern tile 0 on, the shield (`TILES_SHIELDS_ADDRS_INDEX`, 6 tiles) to tile `$30` and the weapon (`TILES_PLAYER_WEAPON_ADDRS_INDEX`) to tile `$38` (`$34` for the Dragon Slayer). A tile id is an index of 16-byte tiles from `TILES_ARMOR_START`, `TILES_SHIELDS_START` or `TILES_WEAPONS_START`.
- **Frames** ("appearances", `TILEINFO_PLAYER_ADDRS`, bank 7, entries are the address minus `$8000`): a four-byte header (rows-1 and columns-1 in the nibbles, x offset, y offset, pivot) then the cells, row by row: a tile number and an attribute, or the single byte `$FF` for an empty cell. Frame number: body = `PLAYER_BODY_TILEINFO_START_OFFSETS[armour*2 + shield bit]` + 0-7 (0-2 walking, 3 crouching or in the air, 4-6 attacking, 7 climbing); weapon `$40 + 8 * weapon` + the same frame; shield `MAYBE_SHIELD_SPRITE_PPU_OFFSETS[frame]` (`$60-$62`, `$42`); at the third attack frame an extra arm piece (`$63-$6A`) 8 pixels behind or 16 in front. Facing left ($40 in `Player_Flags`) flips each tile and mirrors the cells around the pivot.
- **Position.** A sprite's y is the OAM value: the hero's `Player_PosY` + the frame's y offset + 32 (the HUD) + 8 per row; the NES shows it one line lower. The game draws before it moves, so a snapshot of the state after a frame is one step ahead of the sprites.
- **Colours.** Sprite palettes 0 and 1 (attribute bits 0-1) from bank 11 (`$1C0` outside, `$1D0` inside); colour 0 is see-through. Where parts overlap, later drawn is in front: body, weapon, shield (all seven equipments agree with jsnes' picture; the game's OAM order itself is shuffled by its slot allocation).
- **The mantra and the text boxes** (E2/E4; `tools/password_model.py` is the model, `tools/refnes/passwordgolden.mjs` runs the Europe ROM's own routines in jsnes and `tests/test_password.py` checks the model against them; `src/password.s` is the 68000 coder and `tests/test_password_asm.py` checks it against the model on machine68k; `src/text.s` the boxes). The password is a bit string, most significant bit first: 8 bits of checksum (the sum of all bytes is 0 mod 256), 5 bits for the number of characters, then the state, padded to a byte, and a last byte of 0; six bits make a character of `ABC...Zabc...z0123456789,?`. The state: spawn point 3 bits, rank 4, special items 8, quests 8; the selected weapon, armour, shield (2 bits each), spell (3) and item (5), each with a set bit in front (none is $FF); then a count and the entries of the weapons, armours, shields (3 bits and 2 each), spells (3 and 3) and items (4 and 5). The Europe ROM refuses more than the entry screen's 32 characters, a state without armour, a spell of 5 or more, items that are not one of 21 (11, 14 and 17 are not), more than 4 entries (8 items). **The ROM's labels for bank 12 are the US build's addresses and are wrong for the Europe ROM past `Password_Load`**; the golden script has the Europe addresses ($9729, $9735, $9894, $95E9). **The ROM shows the password only when a Guru in a temple meditates with him** (`IScriptAction_ShowPassword`; the death box only says to remember it). The port has no Gurus yet, so the P key shows it in a box (16 characters to a line, as the ROM's text box is 16 wide); the state is the rank, the spell chosen and the equipment the build gave him (`pw_build`; there is no inventory yet). The start menu (`make viewer VIEWER_DEFS="--defsym MENU=1"`, always on in `make viewerdisk`) offers *Start* and *Enter mantra*: a grid of the 64 characters with DEL and END as in the ROM's password screen (stick or arrows move, fire or Space takes the cell, Return is END; END with nothing written goes back), the ROM's "Mantra is in the wrong." for a refused one. An accepted mantra starts the game as after a death with its rank (so its experience and gold), the spell, and power and magic 80; the spawn point is kept in `hero_spawn` and does nothing until there are temples. **Text**: the font is 96 glyphs of 8 bytes at the start of bank 13 (one bit a pixel, the ROM draws them in colour 3), the messages follow it from $8300 (ended by $FF, numbered from 1; $FE a new line, $FD a space, $FC waits for a button, $FB is the rank); `tools/faxanadu_text.py` reads them, `build_assets.py` writes `text.bin` (the font and the few texts the program shows). The port draws a glyph in the brightest colour of the palette on black (`text_color`), straight into the screen on show, and makes both screens again when a box goes (`box_leave`), so a box covers the window but not the HUD. The ROM waits for a button after each four lines; the port has one box for the whole message.
- **Not done yet:** climbing (frame 7 and its flip every 16 ticks is coded from the disassembly, never compared with a ladder in the harness), the sprite being drawn behind background blocks (`Player_CalculateVisibility`: blocks of type 4, 9 and 13), death frames (he has no casting pose in the ROM either), the inside sprite palette.
- **On the ST** (`src/viewer.s`, `blit_tile`): a sprite tile is 8 lines of a mask and four plane bytes (40 bytes), made by `tools/st_convert.py` for each (tile, palette, flip) the pose uses; it is shifted into the plane words and cut at the top of the window and the bottom of the screen. Pixel-exact in Hatari (`tests/test_viewer.py`: five pixel phases, cut at the top and the bottom). **Budget: this blitter takes about 600 cycles a line, 5,000 a tile, 50,000 for a hero: too slow for a frame with the background put back. For the game: compose a pose once into a mask and four planes (about 24x32 pixels) and shift that, or keep sprites word aligned.** Measure first.

## 5f. Sound [verified: the 68000 player against a Python player; the viewer in Hatari plays Eolis's song frame by frame]

The songs and sound effects are not read from the ROM's tables. The ROM's own sound engine (bank 5, a different one in Europe) plays them in the headless NES (`tools/refnes/soundrec.mjs`, run by `tools/record_sounds.py`) and what each channel sounds like after every frame is recorded: 16 songs (`Music_Current` 1-16; 1 and 12 end, the others loop) and 28 sound effects (`SoundEffect_SetCurrent`; 23 is silent). The PAL NES runs its engine at 50 Hz, the same as the ST's VBL: one NES frame is one ST frame.

`tools/build_sound.py` turns that into YM2149 registers: pulse 1 is tone A, pulse 2 tone B, the triangle tone C an octave down, the noise the noise generator on channel C (with the triangle it is both, as loud as the louder). The NES' period t gives the YM period `(t+1) * 2 MHz / 1662607` (PAL CPU clock; the Europe note table is tuned for it). Volumes are 3 dB steps, the triangle (no volume on the NES) is level 12, the pulse duty is ignored (the YM only has a square wave). A song is cut where it starts to repeat (the length counters of the NES drift against the frames, so a note now and then ends a frame early: the loop is the shortest length with the fewest differences) and stored as changes from frame to frame, about 3 bytes a frame; all songs together are 150 KB, 15 KB at most for one. A sound effect takes over the channels it uses from its first sound to its last and gives them back.

`src/sound.s` (included by `frame.s`) plays it from the VBL: `sound_init` (a0 = the data, a1 = room for the song that plays, `SND_SONG_MAX` bytes; the viewer finds both by their offsets from link.ld, because they are last in the image). The songs are packed in the file (`build_sound.pack_songs`, tools/lz.py; 150 KB become 37 KB) and `sound_play_music` unpacks the one it plays (`unpack`, `src/unpack.s`, which the package loader uses too), `sound_play_music` (d0 = 1-16, 0 stops), `sound_play_sfx`, `sound_tick`. The viewer plays song 7 (`MUSIC`, Eolis's) and has debug keys: F1-F10 songs 1-10 (Ctrl 11-16), the digit keys sound effects 1-10 (Ctrl 11-20, Shift 21-28), Backspace stops. Register 14 (the floppy lines) is never touched.

Open: the right song for each area and event (`Areas_DefaultMusic`, the hour glass, the shop and so on), a sound effect that stops another one (the ROM has priorities), the duty cycle, and judging it on the real machine.

## 7. 68000 and GNU as pitfalls (from the Zelda port)

- A `bsr`/`bra`/`Bcc` or `(label,pc)` that does not reach wraps silently: `check_reach.py`.
- `(label,pc)` cannot be a destination: load the address with `lea label(%pc),%aN` and store through it.
- Odd addresses fault on word and long accesses.
- A routine that clobbers `a0`/`a1` inside the caller's loop: save what the callee uses.
- Hardware registers and `$0-$7FF` need supervisor mode (`Super(0)`); restore everything TOS had (palette, video base, the keyboard vector) before `Pterm0`.
- `|` starts a comment in GNU as for m68k. Register names are `%d0`, `%a0`.
- More in the Zelda port's `AGENTS.md`; copy what applies.

## 7b. Display decision (the author, 3 Nov 2026, replaces the overscan idea)

A normal 320x200 screen, no overscan. The HUD sits on top as in the original: its 32 lines (a 256-pixel-wide strip, centred), then a **window of 168 lines** of the 208-line playfield, 256 pixels wide, centred (32 spare pixels on each side). The window follows the hero up and down inside the 208 lines (a camera offset of 0 to 40 lines). Horizontal scrolling between screens and the vertical ones work as in the ROM (256 pixels in 64 frames at 4 pixels).

The overscan test (`src/overscan_test.s`, `make overscan`, bottom border opened in Hatari with a timer B interrupt) is shelved. It worked in Hatari and was never tried on the real machine; the notes are kept here in case: timer B (event count, data 199) fires at the end of line 261; write 0 to `$FF820A` at once and 2 about 500 cycles later (Hatari wants 60 Hz on line 262 before cycle 502 and 50 Hz only after it). It is not part of `make check`.

## 8. Deliberate differences from the ROM

- **Hero at the very edge in the first scroll step.** The ROM computes a sprite's x in 8 bits: a sword can show up at the far edge and the body can be dropped when he stands within a few pixels of the edge. The port clips by position instead. The test leaves the hero's lines out at that one step.
